# Release-ready development protocol (Sohojkor)

This change defers expensive acceptance on ordinary **draft PRs targeting Main only**. Keep work branches without PRs while actively iterating, or use a draft PR for collaboration. Consolidate and locally test changes, then mark ready for review once. That event triggers all the same original full and path-specific acceptance jobs. Do not push incremental edits while the exact ready candidate is being tested; if a genuine defect requires edits, return to draft, fix and retest, then mark ready. Never use skip-ci instructions.

Drafts run the Pages aggregate job's lightweight locked install and typecheck. The aggregate deliberately withholds release acceptance (non-success) on drafts, because GitHub treats skipped required checks as success. A draft is not a failed product release. Existing ws5 integration branches and non-Main PRs retain their current acceptance behavior. Existing Main and manual triggers, job names, path filters, test commands, permissions, production gates, recovery and live browser checks are preserved. Existing open PRs only inherit the new workflow when reconciled with Main; coordinate their owners and do not overwrite their work.

Release sequence: freeze candidate; verify it contains current Main; verify successful (not skipped) exact-head acceptance workflows; independently back up and restore exact pre-release Main; recheck base/head; protected merge; exact Main SQL + Office gate; verified production artifact and live browser checks. Never interpret a green draft/typecheck or skipped job as release acceptance. Repository protection configuration is not changed.

The target is fewer runner allocations during development, not a guaranteed reduction in release duration. Historical GitHub workflow rows remain visible, and draft events may still create skipped workflow rows. Measure actual job allocation, queue time, ready-to-verified-live duration and comparable p50/p95 before declaring optimization complete.
